# PRD-32 — VMI PoStatus Container-Aware Trigger 재설계

> 상위 관련 PRD:
> - PRD-17 PO Lifecycle 통합 이력 (`VMI_PO_STATUS_HISTORY` 데이터 소스 — `markXxx` 도메인 메서드 명세)
> - PRD-22 PO Status History 화면 노출 (이력 읽기 뷰)
> - PRD-23b Dashboard Send On PoStatus Transition
> - PRD-25 SAP IF 전송 트리거 (입고확정 시 IF 송신)
> - PRD-26 ShipmentProcessStatus derive
> - PRD-27 Booking Auto Trigger
> - PRD-30 PoStatus Domain Event 화 (Phase 1 머지, Phase 2~ 보류)
> - PRD-31 컨테이너 매핑 모델 도입 (v22 Container.STATUS DROP, v24 PO.SHIPMENT_ID DROP)
>
> 결정 정책: **PRD-31 이후 1 PO ↔ N Container ↔ N Shipment N:N derived 모델로 전환되면서, PO Status 트리거가 여전히 "1 PO = 1 Shipment" 시절의 알고리즘을 사용하여 last-writer-wins 로 사실과 어긋남.** 본 PRD 는 `PoStatus` enum 9단계와 도메인 메서드 시그니처를 모두 유지하면서, **그 PO 에 적재된 활성 Container 들의 최저 단계(min stage) 로 PO Status 를 산출하는 순수 함수**(`PoStatusDerivation`) 를 추출하고, 기존 트리거 진입점(Shipment / Inbound / Container Service) 안에서 이를 호출하도록 알고리즘만 교체한다. 모든 단계의 부분 진도(부킹/출항/도착/입고) 는 응답 DTO 의 `containerStageCounts` derived 필드로 일관 표현하고 운영자에겐 그리드 보조 표시(`BOOKED (2/3)`, `IN_WAREHOUSE (2/3)`)로 가시화한다.
>
> **명시적 비결정**:
> - `PoStatus` enum 신규 단계 추가하지 않음. `PARTIAL_BOOKED` / `PARTIAL_SHIPPED` / `PARTIAL_ARRIVED` / `PARTIAL_IN_WAREHOUSE` 모두 도입 안 함 — IF 페이로드 호환 비용과 enum 비가역성 회피.
> - 다차원 진도 벡터 모델 도입 안 함.
> - Container.STATUS enum 부활 안 함 (PRD-31 v22 결정 유지).
> - `VmiPoStatusReconciler` Application Service 신설 안 함 (PRD-31 v22 의 NO-OP 축소 결정 유지). 본 PRD 에서는 산출 함수만 추출하고, 호출 책임은 기존 Service 진입점에 남긴다.
> - 출고 트리거(`applyOutboundCleared`) 손대지 않음.

## 1. 배경

### 1.1 PRD-31 이후 데이터 모델

PRD-31 v22/v24 적용 후 PO ↔ Container ↔ Shipment 관계는 다음과 같다.

```
VmiPoHeader (계약/회계 단위)
   └─ VmiPoDetail (자재 단위)
        └─ VmiContainerItem (적재 분할, N:N 중간)
             └─ VmiContainer (운영 흐름 1차 단위)
                  ├─ Container.shipmentId → VmiShipment (N:1)
                  └─ VmiInboundHeader.containerId (1:1, 도착 후 발번)
                       └─ VmiInboundItem (PO Item 단위 입고 진도)
```

- `VmiContainer` 는 단계 정보 없음 (PRD-31 §5.9). 단계는 **Shipment ProcessStatus** 와 **Inbound 확정 여부** 가 1차 소스.
- `VmiPoHeader.shipmentId` 컬럼 제거됨 (PRD-31 §5.10). PO ↔ Shipment 는 Container 경유 N:N derived.
- `VmiInboundHeader.containerId` 컬럼 추가됨 — 입고 단위가 PO → Container 로 이전.

### 1.2 현행 트리거 알고리즘의 한계

**한계 1 — Last-writer-wins (Shipment 트리거)**

`VmiShipmentServiceImpl.applyShipmentChangeToAllPos(shipmentId, before, after)` 는 1 Shipment 의 단계 차분(before → after) 만 보고, 그 Shipment 에 묶인 모든 PO 에 `applyShipmentProcessStatusChange(before, after)` 를 일괄 호출한다.

문제: 1 PO 가 여러 Shipment 에 분산된 케이스(예: C1 → Shipment-X, C2 → Shipment-Y)에서, Shipment-X 가 IN_TRANSIT 으로 진입하면 PO 가 SHIPPED 가 된다. 하지만 C2 는 Shipment-Y 의 DRAFT 단계에 있다 — PO 의 사실은 BOOKED 미만이어야 한다.

**한계 2 — 첫 Container 입고 시 PO 전체 IN_WAREHOUSE (Inbound 트리거)**

`VmiInboundServiceImpl.transitionPoToInWarehouse(poId, …)` 는 헤더 1건의 입고확정 시점에 `po.markInWarehouse()` 를 호출한다. 1 PO 의 Container 중 1개만 입고확정 되어도 PO 전체가 IN_WAREHOUSE 로 마킹된다.

**한계 3 — 부분 진도의 비가시화 (모든 단계 공통)**

PoStatus 단일 enum 은 1 PO 의 Container 단계 분포를 표현할 수 없다. 운영자는 그리드에서 PO 의 진도를 알 수 없어 매번 Detail Panel 을 펴야 한다. **이 비가시화는 입고 단계만의 문제가 아니라 부킹/출항/도착 모든 단계에 동일하게 존재**한다 — 부분 BOOKED, 부분 SHIPPED, 부분 ARRIVED, 부분 IN_WAREHOUSE 모두.

## 2. 목표 (In-Scope)

### 2.1 PoStatus 산출 규칙 (Container-Aware)

| # | 항목 | 동작 |
|---|------|------|
| F-1 | Container 의 effective stage 산출 함수 | `containerStage(container, shipmentProcessStatus, inboundConfirmed) → PoStatus` — 본 PRD §4.1 참조 |
| F-2 | PO 의 derived stage = `min(activeContainers.map(containerStage))` | 활성 Container (`delYn = 'N'`) 만 대상. 산출 결과는 CONFIRMED/BOOKED/SHIPPED/ARRIVED/IN_WAREHOUSE 5단계 중 하나 (NEW 는 운영자 명시 확정 전 단계라 산출 결과로 도출되지 않음) |
| F-3 | Container 가 0개인 PO 의 derived stage | PO 의 현재 `status` 그대로 유지 (`NEW` / `CONFIRMED` / `CANCELLED`). PRD-31 §F-PO-5 동선과 정합 — Container 미배정 PO 는 Shipment 화면에서 묶기 대기 |
| F-4 | `VmiPoHeader.applyDerivedStatus(derived)` 가드 확장 | 기존 PARTIAL/COMPLETED 보호 + IN_WAREHOUSE 에서 ARRIVED 이하로 강등 금지. 출고 진행 PO 는 Outbound 축이 단독 책임 |

### 2.2 산출 함수 추출 — `PoStatusDerivation`

순수 함수 클래스로 산출 규칙을 단일 소스에 모은다. **별도 Application Service / Reconciler 클래스 신설하지 않음** — Container 단계 변경의 호출 책임은 기존 Service 진입점이 유지한다 (PRD-31 v22 의 Reconciler NO-OP 결정 존중).

| # | 항목 | 동작 |
|---|------|------|
| P-1 | `PoStatusDerivation.derive(List<ContainerStageView> containers, PoStatus currentStatus) → PoStatus` | 활성 Container 들의 단계 뷰를 받아 derived PoStatus 산출 |
| P-2 | `PoStatusDerivation.containerStage(ContainerStageView view) → PoStatus` | 단일 Container 의 effective stage 매핑 (§4.1) |
| P-3 | `ContainerStageView` value object | `containerId`, `shipmentProcessStatus`, `inboundConfirmed` 보유 — Repository 가 일괄 로드해서 채움 |
| P-4 | 단위 테스트 | 매핑 표 5가지 + min-stage 케이스 5가지 + 빈 Container 케이스 1가지 등 도메인 단위 테스트 작성 — `feedback_test_scope.md` 정합 (자동 계산/불변식 보유 도메인) |

## 3. 비대상 (Out-of-Scope)

- **`PoStatus` enum 신규 단계 도입** — `PARTIAL_BOOKED` / `PARTIAL_SHIPPED` / `PARTIAL_ARRIVED` / `PARTIAL_IN_WAREHOUSE` 모두 도입 안 함. 부분성은 derived 카운터로만 표현 → 모든 단계 일관성 확보 + IF 페이로드 호환 + enum 비가역성 회피.
- **다차원 진도 벡터 모델 (옵션 A)** — JSON / 카운터 컬럼군으로 PO Status 를 다차원화하지 않음.
- **Container.STATUS 컬럼 부활** — PRD-31 v22 결정 유지. 단계 정보는 Shipment ProcessStatus + Inbound 확정 여부 가 단독 책임.
- **`VmiPoStatusReconciler` Application Service 신설** — PRD-31 v22 의 NO-OP 축소 결정 유지. 호출 책임은 기존 Service 진입점에 남긴다. Reconciler 패턴 재도입은 PRD-30 Phase 2 도메인 이벤트화 재개 시점 또는 트리거 도메인이 3개 이상으로 늘어날 때(Rule of Three) 재검토.
- **출고 트리거 변경** — `VmiOutboundServiceImpl.updatePoStatusByDiCleared` 수량 누적 산출 그대로. PRD-20 멀티-PO 그룹 모델과 정합.
- **`applyShipmentProcessStatusChange` / `markBooked` / `markShipped` / `markArrived` / `revertX` 도메인 메서드 삭제** — 도메인 메서드 시그니처 유지. 본 PRD 는 호출 알고리즘만 교체. 메서드는 향후 운영자 명시 액션 또는 외부 호출에서 재사용 가능.
- **도메인 이벤트화 (PRD-30 Phase 2~)** — 본 PRD 는 동기 호출 패턴. 이벤트 패턴은 PRD-30 Phase 2 재개 시점에 본 산출 함수를 이벤트 핸들러로 감싸는 형태로 통합.
- **기존 데이터 마이그레이션 스크립트** — VMI 가 개발 단계(`project_vmi_dev_phase.md`)이므로 데이터 전량 삭제 후 신규 트리거로 재구축. 운영 데이터 대상 산출 SQL 미작성.

## 4. 동작 정책

### 4.1 Container Effective Stage 매핑 함수

각 활성 Container 의 단계를 PoStatus 로 환산하는 순수 함수.

```
containerStage(container, shipmentProcessStatus, inboundConfirmed) → PoStatus
```

| 조건 | 결과 단계 |
|------|-----------|
| Container 가 Shipment 미배정 (`shipmentId == NULL`) | `CONFIRMED` |
| Shipment 단계 = DRAFT | `CONFIRMED` |
| Shipment 단계 = BOOKED | `BOOKED` |
| Shipment 단계 = IN_TRANSIT / ARRIVAL_SOON | `SHIPPED` |
| Shipment 단계 = ARRIVED, Inbound 미확정 | `ARRIVED` |
| Shipment 단계 = ARRIVED, Inbound 확정 (`VmiInboundHeader.dtEntradaEntreposto IS NOT NULL`) | `IN_WAREHOUSE` |

비고: Inbound 확정 여부는 `VmiInboundHeader.dtEntradaEntreposto` 의 NULL 여부로 판단 (PRD-31 §4.1 흐름과 정합). 헤더가 존재하지 않거나 dtEntradaEntreposto 가 NULL 이면 미확정.

### 4.2 PO Derived Stage 산출 알고리즘

```
1. PO 의 활성 Container 목록 수집 (delYn='N', PoItem 보유)
2. Container 0개 → derived = po.currentStatus (변경 없음)
3. 각 Container 의 containerStage(...) 산출
4. derived = min(stages, byPoRank)
   - byPoRank: NEW(0) < CONFIRMED(1) < BOOKED(2) < SHIPPED(3) < ARRIVED(4) < IN_WAREHOUSE(5)
5. po.applyDerivedStatus(derived) → 가드 통과 시 status 변경
6. 변경 발생 시 history 적재
```

### 4.3 `applyDerivedStatus` 가드 규칙 (확장)

기존 가드 (PARTIAL/COMPLETED 인 경우 IN_WAREHOUSE 이하 derived 무시) 에 다음 규칙 추가:

| 현재 status | derived 단계 | 동작 |
|-------------|------------|------|
| NEW | 어떤 단계든 | 무시 — Container 가 생겨도 NEW 는 운영자 명시 확정(`markConfirmed`) 거치기 전엔 변경하지 않음 |
| CANCELLED | 어떤 단계든 | 무시 |
| PARTIAL / COMPLETED | IN_WAREHOUSE 이하 | 무시 (기존 가드) |
| IN_WAREHOUSE | ARRIVED 이하 | 무시 — 입고 확정된 PO 가 Container 단계 변경으로 강등되지 않음 (입고 취소는 별도 명시 흐름) |
| 그 외 | 그 외 | derived 적용 |

### 4.4 호출 흐름 — Shipment 단계 변경

```
[운영자] booking/etd/eta/접안일 입력 → VmiShipmentServiceImpl.updateShipment
   ├─ shipment.update(...)
   ├─ 영향 PO 목록 = poHeaderRepository.findByShipmentIdViaContainer(shipmentId)
   └─ recomputeAndApply(poIds, ctx={SHIPMENT, "updateShipment", "SHIPMENT", shipmentId, reason})
       ├─ stagesByPo = containerRepo.findActiveByPoIdsWithStage(poIds)
       └─ 각 PO 마다:
            ├─ derived = PoStatusDerivation.derive(stagesByPo[poId], po.status)
            ├─ po.applyDerivedStatus(derived) → 가드
            └─ 변경 시 history 적재 (단일 행)
```

`recomputeAndApply` 는 `VmiShipmentServiceImpl` 의 private 헬퍼. 다른 Service 에서도 동일 패턴 (`containerRepo.findActiveByPoIdsWithStage` + `PoStatusDerivation.derive` + `applyDerivedStatus` + history 적재) 을 반복하지만, 두 곳 이상 중복되는 시점에서 `winus-common` 또는 도메인 패키지 utility 로 분리 검토 (`feedback_util_extraction.md`).

### 4.5 호출 흐름 — Inbound 확정

```
[운영자] Inbound 상세 → "입고 확정" 버튼 → VmiInboundServiceImpl.confirmEntradaByNo
   ├─ 묶인 헤더들의 dtEntradaEntreposto 채움
   ├─ 재고 적재 (VmiInventoryService.increaseStock)
   ├─ 영향 PO 목록 = 헤더들의 PO_ID distinct
   ├─ recomputeAndApply(poIds, ctx={INBOUND, "confirmEntrada", "INBOUND", inboundId, "입고 확정 [...]"})
   └─ Whirlpool IF 송신 (기존 try-catch 격리 유지)
```

부분 입고 케이스: 1 PO 의 Container 3개 중 2개만 같은 INBOUND_NO 에 묶여 확정되면, derived = min(IN_WAREHOUSE, IN_WAREHOUSE, ARRIVED) = ARRIVED → PO Status 는 ARRIVED 유지. 그리드는 `ARRIVED (2/3 보세창고 입고완료)` 로 표시.

### 4.6 호출 흐름 — Container 변경

```
VmiContainerServiceImpl.create(request)
   ├─ Container + Items 저장
   ├─ Shipment 자동 묶음 (request.shipmentId 가 있으면)
   └─ recomputeAndApply(affectedPoIds, ctx={SHIPMENT, "createContainer", "CONTAINER", containerId, reason})

VmiContainerServiceImpl.cancel(containerId)
   ├─ container.markDeleted() (delYn='Y' cascade)
   └─ recomputeAndApply(affectedPoIds, ctx={SHIPMENT, "cancelContainer", "CONTAINER", containerId, reason})

VmiContainerServiceImpl.assignToShipment(containerIds, shipmentId)
   ├─ 각 Container.assignToShipment(shipmentId)
   └─ recomputeAndApply(affectedPoIds, ctx={SHIPMENT, "assignContainerToShipment", "SHIPMENT", shipmentId, reason})
```

### 4.7 멱등성

산출 함수 호출은 멱등이다 — 같은 입력 상태에서 여러 번 호출해도 결과 동일. NO-OP 일 땐 history 도 적재하지 않음. 향후 batch 일괄 보정/장애 복구 시점에 활용 가능.

### 4.8 동시성

본 PRD 에서는 비관적 락 도입하지 않음. PRD-31 흐름과 동일한 트랜잭션 격리 전제. 산출 함수 호출은 호출자 트랜잭션에 합류 (`Propagation.REQUIRED`).

만약 운영 중 last-writer-wins 가 다시 문제되면 후속 PRD 에서:
- (a) PO 단위 비관적 락 (`SELECT ... FOR UPDATE`), 또는
- (b) AFTER_COMMIT 이벤트 + 재시도 패턴

도입 검토. 현 단계는 단순 트랜잭션 동기 호출로 충분.

## 5. 구현 세부 (참고)

### 5.1 `PoStatusDerivation` 골격

```java
public final class PoStatusDerivation {

    private PoStatusDerivation() {}

    /**
     * 활성 Container 단계 뷰들로부터 PO derived stage 산출.
     * Container 가 비어 있으면 currentStatus 그대로 반환.
     */
    public static PoStatus derive(List<ContainerStageView> containers, PoStatus currentStatus) {
        if (containers == null || containers.isEmpty()) {
            return currentStatus;
        }
        return containers.stream()
                .map(PoStatusDerivation::containerStage)
                .min(Comparator.comparingInt(PoStatusDerivation::rank))
                .orElse(currentStatus);
    }

    /** §4.1 매핑 표 */
    public static PoStatus containerStage(ContainerStageView v) {
        if (v.shipmentProcessStatus() == null) return PoStatus.CONFIRMED;
        return switch (v.shipmentProcessStatus()) {
            case DRAFT -> PoStatus.CONFIRMED;
            case BOOKED -> PoStatus.BOOKED;
            case IN_TRANSIT, ARRIVAL_SOON -> PoStatus.SHIPPED;
            case ARRIVED -> v.inboundConfirmed() ? PoStatus.IN_WAREHOUSE : PoStatus.ARRIVED;
        };
    }

    private static int rank(PoStatus s) {
        return switch (s) {
            case NEW -> 0;
            case CONFIRMED -> 1;
            case BOOKED -> 2;
            case SHIPPED -> 3;
            case ARRIVED -> 4;
            case IN_WAREHOUSE -> 5;
            default -> Integer.MAX_VALUE;
        };
    }
}
```

## 6. 결정사항 (확정 — 사용자 위임 받아 추천안 채택)

### 6.1 산출 모델 — **옵션 B (단일 enum + min-stage 산출 규칙)**

PoStatus enum 9단계 유지. derived 카운터로 진도 보조 표시.

대안 폐기:
- 옵션 A (다차원 진도 벡터) — PRD-23b/PRD-25 IF 페이로드 호환 비용 과대, 다운스트림 영향 광범위
- 옵션 C (Container.STATUS 부활) — PRD-31 v22 결정 직접 번복
- 옵션 D 변형 — `PARTIAL_IN_WAREHOUSE` 만 신설 (입고 단계만 부분 enum 도입) — 다른 단계(부킹/출항/도착) 의 부분성과 비일관. enum 4개(`PARTIAL_BOOKED/SHIPPED/ARRIVED/IN_WAREHOUSE`) 모두 추가는 IF 페이로드 비용 과대 → derived 카운터로 통일

### 6.2 산출 단위 — **Container 수**

Container 가 운영 흐름의 1차 단위 (PRD-31 §1 결정 정합). PO Item 수량 합계 단위는 출고 축이 단독 책임.

### 6.3 트리거 시점 — **동기 산출**

배치 아닌 동기 호출 (`Propagation.REQUIRED`). 트랜잭션 일관성 우선. 비동기 도입은 PRD-30 Phase 2 재개 시점에.

### 6.4 History 다단계 분해 폐지 — **단일 행 적재**

derived stage 산출 결과를 단일 행으로 적재. 기존 `applyShipmentProcessStatusChange` 다단계 분해 (ARRIVED → SHIPPED → BOOKED → CONFIRMED 3건) 폐지.

### 6.5 출고 진행 PO 보호 — **derive 강등 금지**

PARTIAL/COMPLETED PO 에는 derived 적용 안 함 (기존 가드). IN_WAREHOUSE 에서 ARRIVED 이하 강등도 금지 (입고 취소는 별도 명시 흐름).

### 6.6 Shipment 미배정 Container — **CONFIRMED rank**

Container 가 생성됐지만 Shipment 미배정 (`shipmentId IS NULL`) 인 단계는 `CONFIRMED` rank. PRD-31 §4.1 흐름과 정합 — PO 확정 후 Shipment 묶기 전 단계.

### 6.7 부분 진도 표현 — **derived 카운터로 모든 단계 일관 표현**

`PARTIAL_XXX` enum 4단계 신설 안 함. PoStatus enum 9단계 그대로. 부킹/출항/도착/입고 모든 단계의 부분성은 응답 DTO 의 `containerStageCounts` 와 그리드 보조 텍스트 (`BOOKED (2/3)`, `IN_WAREHOUSE (2/3)` 등 동일 형식) 로 표현.

### 6.8 Reconciler 신설 보류 — **PRD-31 v22 결정 유지**

`VmiPoStatusReconciler` Application Service 신설 안 함. 호출 책임은 기존 Service 진입점이 유지. 본 PRD 는 산출 규칙을 `PoStatusDerivation` 순수 함수로만 단일 소스화한다.

Reconciler 패턴 재도입은 다음 조건 중 하나가 만족될 때:
- (a) PRD-30 Phase 2 도메인 이벤트화 재개 — 이벤트 핸들러가 자연스럽게 Reconciler 가 됨
- (b) PoStatus 트리거 도메인이 3개 이상으로 늘어남 (Rule of Three — 현재 Shipment/Inbound/Container 3곳이지만 모두 같은 동기 호출 패턴이므로 응집도 충분)
